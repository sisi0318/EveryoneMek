# OverloadCore 装备扩展方案

研究日期：2026-09-27。基于当前 OverloadCore alpha.15、Minecraft 1.21.1、Mekanism 10.7.19.85、Curios 9.5.1。

**本文是经源码核对的实现方案，以下新模块、改装入口和武器尚未实现；不改变当前游戏版本。**

## 方向

以 Mek 原生装备模块为统一升级方式：MekaSuit／MekaTool 接新模块，现有饰品补充模块容器与佩戴中改装，独立武器沿用相同模块、储能和配置体系。保留过载核心的代价与雷印的用途，不让新装备只剩更大的伤害数字。

普通模块不强制要求佩戴诅咒核心；只有使用“余雷”、补偿磁枷／劫热的联动功能依赖核心。雷印继续独立可用，基本救命费用仍为 **100,000 FE／次、无冷却**，普通／极限抽能、所有权与明确授权照常生效。

## 已核对的原生入口

对照本地同版本发布源码 JAR 与运行实现，在线官方分支仅辅助定位，不以开发分支代替发布契约。

| 需求 | 当前 Mek 提供的入口 | 仍需由 OverloadCore 完成 |
| --- | --- | --- |
| 给 MekaSuit／MekaTool 加模块 | `ModuleData`、`ICustomModule`；`MekanismIMC.addMekaSuit*Modules`／`addMekaToolModules` | 自己的模块物品、配方、参数和实际能力 |
| 把新武器／饰品变成模块容器 | `IModuleHelper.applyModuleContainerProperties`；`MekanismIMC.addModuleContainer` 与自有 IMC 消息 | 明确支持清单、储能容器、模式和行为调用，不能宣称兼容所有原生模块 |
| 安装／拆卸 | `TileEntityModificationStation` 接受已注册的模块容器，检查兼容性及安装上限 | 绑定且不可摘下的饰品需要佩戴中改装入口 |
| 多级／模式／HUD | `ModuleDataBuilder.maxStackSize`、配置项、互斥标记、HUD 与模式接口 | 服务端效果、实际耗能以及 Curios 上的调用桥接 |
| 装備抵抗 | `ICustomModule.getDamageAbsorbInfo` 被 MekaSuit 的伤害吸收路径调用 | 当前雷印的死亡／移除保护继续独立，不能由一般护甲模块替代 |
| 随身充电 | 原生 `ModuleChargeDistributionUnit` 已遍历 Curios 并使用 `IStrictEnergyHandler` | 储能饰品正确暴露真实可充电容器，处理保护快照中的合法能量变化 |
| 外装模型 | `IModuleHelper.addMekaSuitModuleModels`／`addMekaSuitModuleModelSpec` | 原创 OBJ 外装、启停外观；武器和 Curios 另外接自己的 renderer |

原生 `ModuleTweakerContainer` 只列护甲、快捷栏和副手，没有已佩戴的 Curios 槽。`ICustomModule.tickServer` 由 MekaSuit 的物品逻辑调用；给饰品注册容器不会自动产生佩戴效果。原生攻击增幅在 MekaTool 中有明确的数值与扣能调用，新的连锁攻击不能只注册一个名字。

参考：[官方 IMC](https://github.com/mekanism/Mekanism/blob/1.21.x/src/api/java/mekanism/api/MekanismIMC.java)、[自定义模块接口](https://github.com/mekanism/Mekanism/blob/1.21.x/src/api/java/mekanism/api/gear/ICustomModule.java)、[1.21.1 物品组件](https://docs.neoforged.net/docs/1.21.1/items/datacomponents/)。

## 建议的首批模块

名称为设计名；等级、功耗与上限在实现时配置化并验证，当前不修改数值。

| 模块 | 安装位置 | 实际玩法 | 能源与限制 |
| --- | --- | --- | --- |
| 余雷耦合单元 | MekaSuit 胸甲 | 将核心回收电更快地送入胸甲，再由 Mek 原生充电分配模块供应工具与饰品 | 消耗现有核心缓冲，不新增回收来源、不重复充电；未安装时保留原基础充能能力 |
| 相变热沉单元 | MekaSuit 胸甲 | 主动降低 OverloadCore 的劫热积累，提高高温车间作业时间 | 持续用电，有功率上限；缺电恢复原规则，不把所有高温／辐射伤害一并免疫 |
| 磁荷补偿单元 | MekaSuit 护腿 | 用电抵消部分磁枷负荷，携带金属时仍能维持一定机动性 | 不删除真实重量或远程扫描仓库；缺电及过载后回到原阈值和恢复滞后 |
| 护命电容单元 | 逆命雷印 | 平时从充电设备／胸甲充电，离开工厂后仍有有限救命储备 | 每次仍付足 100,000 FE；电容与设备共同预检后一次结算，不足不部分扣费 |
| 余雷固相单元 | 逆命雷印 | 升级成功保命后的次数盾 | 只增加有上限的次数／时长，不能叠成无限盾，也不为付费保命新增冷却 |
| 谐振放电单元 | MekaTool | 正常攻击后消耗额外电量，对少量附近敌人产生连锁电弧 | 和原攻击增幅区分；普通伤害流程、目标与距离上限、遮挡与队友判断；防止电弧递归触发自己 |

Mek 已有能量、充电分配、攻击增幅、挖掘、磁吸、飞行、夜视等模块。优先复用这些基础能力；避免仅换名重做一遍。原生能量模块在新容器上也需要实现容量／速率如何随等级变化，不能仅开放安装。

## 独立武器与装备外装

- **磁轨长枪**：服务器判定蓄力与射线命中，使用电能与金属弹丸；弹仓、充能速度、聚焦射程、贯穿作为不同模块。贯穿仅对明确的实体目标规则生效，默认不破坏建筑。先做单发和蓄力，再增加模式。
- **雷铸刃**：以挥砍和蓄力放电区分于工具；储能、刃场范围与电弧模块共用基础设施。正常伤害与护甲结算，不直接操作实体死亡／移除来实现武器伤害。
- **MekaSuit 外装**：胸甲加散热鳍片与小型电容，护腿加磁场环；装了什么模块就出现相应外装。先扩展原装备，暂不复制四件只提高基础数值的新套装。
- Mek Tools 的普通材料剑／护甲不是现成的 MekaSuit 模块容器。若以后支持，需要单独登记和调用适配；不把“属于 Mek”作为无条件通用兼容。
- 武器核心、刃场和电弧可采用低面数模型配合 shader；实体机壳保持粗像素工业风。效果按距离和可见性裁剪，同一批渲染传状态，不靠大量粒子实体，保留关闭效果的回退外观。

## 饰品改装必须先补的三处数据契约

1. **核心恢复保存升级。** 当前 `CoreBinding.restore` 找不到原件时只重建 owner／instance；若直接把模块写进物品，恢复会丢失升级。需要把已认可的模块及配置纳入玩家权威记录，原有回收电量仍只保存一份。
2. **雷印允许合法修改。** `WardLedger.Entry` 是完整物品快照，`WardCustody` 和物品 Mixin 会拒绝普通组件改写。增加范围明确的改装事务：核对菜单、玩家、槽位、同一原件和改装站权限，消耗材料后更新实际模块与保护快照；不得将任意组件变化当作升级授权。
3. **能量是动态数据。** 护命电容在佩戴中充放电也会改变组件，必须有受控的能量写入路径并同步权威数据；不能靠定时恢复旧快照返还已消耗电量。极限抽能不能越过设备禁供和权限规则。

建议在原改装站增加“佩戴饰品”页：已佩戴核心／雷印是只读目标，不搬进机器、不临时解除魂契。玩家选择目标和模块，安装／拆卸由服务端事务完成；返还空间不足则不拆。使用原生 `ModuleContainer` 做模块变更，复用当前依赖公开控件，只有缺少公开入口时才做局部 Mixin。

普通 MekaSuit、MekaTool 和独立武器继续走原改装站。可摘下的雷印也可正常摘下再改装；佩戴中配置、改装都必须更新合法快照。原生模块配置包只认识自己的槽位，Curios 页使用带菜单会话与实际槽位校验的专用请求。

当前 `CoreBinding.charge` 还写死只给原版 `mekanism:meka_tool`／`mekasuit_*` 充能。扩展前改成明确的支持标签／容器能力检查，区分核心到胸甲的充电与胸甲原生分配，按实际接收量扣款，不能用一次泛化扫描造成多路重复转移。

## 实施顺序与验收

1. **MekaSuit 三个模块**：建立原生模块注册与配方，完成余雷耦合、热沉和磁荷补偿；原改装站安装／拆卸、配置启停与真实电耗先跑通。
2. **饰品升级**：先补上述保存／改装事务，再加雷印电容、次数盾模块与佩戴中配置。基本费用、无冷却、摘戴、防丢及原有保护回归保持。
3. **武器**：先 MekaTool 谐振放电，再独立磁轨长枪与雷铸刃。最后接外装模型和 shader，视觉不参与服务器结算。

必要验证按阶段执行：原改装站真实安装／退还；模块关闭与缺电停止；充电守恒；核心重生／异常恢复保留升级；雷印正常配置不被回滚且伪造请求仍被拒绝；电容＋设备的不足退款和单次结算；武器命中／未命中／取消／保护目标与连锁去重。仅存背包不能获得佩戴收益，Curios 与普通装备路径不能同 tick 重复触发。客户端游戏内验收由用户完成。
