# 人造微缩太阳 · 设计初稿

2026-09-24。**设计提案，尚未实现；当前可用版本仍为0.1.0-alpha.7。** 在MekGravity内新增，不建立独立模组。用户已选择“投放长效恒星燃料，点燃后维持很久”；下方尺寸、功率、寿命和配方是本轮建议值，尚未视作用户已确认。

## 1. 定位

玩家名称：**人造微缩太阳**；主控可叫“恒星约束器”，完整多方块统称“微缩太阳”。

它是引力技术之后的长期主电源：将一个封装的恒星燃料放入燃料仓，用外部能量点火，随后由四组采能翼持续取电。平时补的是长效燃料物品，氘氚只出现在燃料制备产线。

| 项目 | 现有引力约束反应堆 | 微缩太阳提案 |
| --- | --- | --- |
| 角色 | 灵活的高功率电源 | 需要较大初期投入的长期主电站 |
| 主体 | 7×7×7封闭立体机架 | 9×9×9八角基座、上下环、四组弧形采能翼 |
| 中心 | 小型深紫核心、反向金属环 | 约2.5格直径的明亮太阳，日冕与日珥 |
| 日常燃料 | 致密燃料丸，终极约30秒/丸 | 恒星燃料，最高档目标约1小时/份 |
| 发电升级 | 六组线圈最低等级 | 约束环限制反应上限，采能翼决定采能上限 |
| 操作 | 供料、负载、启停 | 装料、点火、调节采能负载、自动待机 |

不依赖白天、天气或露天环境；可建在地下工厂。不会给周围普通太阳能板提供额外产能，避免无上限叠加采能。

## 2. 一套完整的玩家流程

1. 用现有Mek产线制备并封装恒星燃料。
2. 摆下恒星约束器，使用结构预览/一键搭建完成9×9×9主体。
3. 燃料仓放入恒星燃料；点火接口接外部电源，发电接口接感应矩阵或工厂电网。
4. 点击“点火”。小光点逐渐膨胀成太阳，采能翼展开，开始供电。
5. 维持燃料仓补货。每份燃料按实际反应消耗能量，耗尽后自动衔接下一份。

只在全新装置首次点火时支付启动电费。普通停机、等待需求、补料和服务器重启不重复支付。缺料可以自动熄灭/回落为待点燃状态，已有点火资格和未耗尽燃料预算保留；补货后恢复。

## 3. 结构：先建模，再做材质

详细逻辑坐标与用料示意由 [结构数据](art/solar-design/layout.json) 和 [结构层图](art/solar-design/layout.svg)保存。示意图用于表达占位，不是已完成的三维模型。

- 固定外包围尺寸9×9×9，地面为削去四角的八角基座，四根角支撑连接上部冠架。
- 上、下各一圈八角约束环，中心留出完整视线；上、下极点各有一个聚束器，形成稳定的竖直轴线。
- 正、背、左、右各一组3×3逻辑占位的采能翼，建模为向太阳弯曲的分片内凹采能面，不做9个重复的小机器正面。
- 太阳中心位于(4.5,4.5,4.5)，实体视觉直径约2.5格；日冕最大半径约1.65格。中心5×5×5区域留作渲染空间，仅(4,4,4)放“恒星胚核”方块，其余发光体由渲染器绘制。
- 基座前沿放主控、燃料仓和点火口；默认背面/侧面各布置两个发电口。所有接口有真实外侧连接面。
- 大面积浅钢灰与石墨色机体，仅太阳、翼片内沿和指示灯使用暖橙/琥珀色。不会把整台机器变成金色或全发光方块。

这次先完成可旋转整机灰模，明确“基座—支撑—环—弧形采能翼—太阳”的厚度和比例，再从确认模型拆回运行部件。图像生成仅制作确认后的16×16材料贴图，不以平面贴图代替立体造型。

默认结构草案共220个实体方块，其他509格为空气，其中包含太阳周围需要保留的渲染空间。详细数量由生成脚本核对；默认图只定义一套可用摆法，未来扩展接口时不能随意替换核心约束部件。

## 4. 长效恒星燃料

建议首版仅增加一个日常燃料：**封装恒星燃料**，不要求玩家轮流投放数种燃料或反复手动续火。

- 单份能量提案：**46.08 PJ = 46,080,000,000,000,000 J**，默认约18.432 PFE毛能量。
- 这是整份燃料的有限预算，包含输出电能和约束自耗。不是每tick重新读取出一个完整寿命。
- 使用同一份燃料预算，更高功率消耗更快。升降级、改变负载、切换红石、重载、拆成带数据物品都不能刷新寿命。
- 电缓存满时停止投入和推进反应，进入“余辉待机”；只留视觉上的小太阳/微光，不偷偷消耗燃料。它属于游戏待机规则，不模拟现实维持等离子体的代价。
- 未加工物品仍归独立燃料仓；主控只保存已经投入的剩余J预算和本批原始总量。剩余能量未用完前，不能再提前吞整仓物品。
- 不默认产生必须手动排出的灰烬/空壳；若后期加入副产物，必须连自动输出一起设计。

### 制备路线

建议使用：**致密燃料压缩 → 反物质封装成燃料坯 → Mek加压反应室注入D-T → 封装恒星燃料**。

燃料坯用致密燃料、反物质与高阶封装材料体现后期成本，具体配比在经济性测试前不锁死。D-T只用于前端制备，不要求太阳一直连着气体管道。

优先接入原Mek加压反应室和JEI分类，不为一条制备配方新造一台机器。已核对当前发布JAR：加压反应室液体与化学品槽上限均为10,000，因此制备配方的**单次化学品/流体数量不能超过10,000**。高总耗料应通过多份中间物压缩，而不是写一个原机器装不下的巨量配方。

初稿候选的加压步骤为：一个燃料坯 + 8,000 mB D-T + 1,000 mB水 → 一个封装恒星燃料。材料成本、时长与制备耗电需要结合整合包实测；这里只确认它符合原机器储罐容量，尚未证明经济性合理。太阳能值是本附属的游戏平衡值，不是从这点D-T推算出的现实能量。

## 5. 功率和扩展

以下均是**待测试的初稿值**，按Mek默认2.5 J/FE和20 TPS计算；先确保新路线值得建，再根据制备成本、供电需求和接收设备吞吐调整。

| 配置档位 | 毛发电上限 | 扣5%自耗后的净发电 | 单份燃料满载时间 |
| --- | ---: | ---: | ---: |
| 初级 | 32 GFE/t | 30.4 GFE/t | 8小时 |
| 高级 | 64 GFE/t | 60.8 GFE/t | 4小时 |
| 精英 | 128 GFE/t | 121.6 GFE/t | 2小时 |
| 终极 | 256 GFE/t | 243.2 GFE/t | 1小时 |

**约束与采能分别升级**：

- 上下环及两个聚束器的最低等级给出反应功率上限。
- 四组采能翼每组提供对应档位的¼采能上限。首版要求每组9块同级、四组可不同级；有效采能上限为四组相加。
- 实际目标毛功率 = min(约束上限, 采能总上限) × 玩家负载设置。升级一组翼片就能增加采能能力，不要求同时做齐所有最高级材料；若约束已满，界面指出应升级约束环。
- 每组翼片只算一次，不能按9个方块重复加9倍，也不能多个控制器共享一组翼片。

点火电费暂定8 TFE，保护备用电256 GFE，整机电缓存16 TFE。每个发电接口暂定64 GFE/t，默认4个合计256 GFE/t；先有足够缓冲再给外部，输出不受当前发电速度限制。原感应矩阵/线缆仍受自己的吞吐约束，不能保证一个原生接口吃满整机。

暂不需要冷却钠、水循环、蒸汽塔或强制维护。氘氚/水属于燃料工厂配方，不是太阳本体的日常条件。磁约束自耗按5%从燃料毛能量里扣，避免额外循环电费难以理解。

## 6. 太阳如何动

- **点火**：中央小白点 → 橙红等离子团膨胀 → 表面开始缓慢转动 → 日冕展开，采能翼内沿逐段点亮。
- **稳态**：白黄亮区、橙红表层与少量深色斑块缓慢漂移；两层不等速旋转，让表面看起来在流动。
- **日珥**：3～5条低频拱形等离子弧从太阳表面升起，再回落到另一处；不做杂乱的满屏闪电。
- **采能**：能量细流从太阳向外翼片流动，方向与引力堆向内汇聚不同；功率上升时，日冕略展开、采能流更明显。
- **待机/停机**：逐渐缩成较暗的赤红火种，再收起采能流；补料/需求恢复后顺滑展开，不突然消失或重新从满寿命开始。

使用已有BER分体渲染/时间插值思路，但新建太阳网格和材质，不把引力核心改成橙色直接复用。太阳本体、表面纹理层、日冕、日珥、采能流各有固定绘制预算；远处减少日珥/光点数量。同步状态和少量负载数据，禁止每个光点都变成实体或数据包。

## 7. 操作界面

沿用Mek窗口，主界面以“这颗太阳还够用多久、正在供多少电”为核心：

- 顶部：运行状态、最低约束等级。
- 中部：恒星燃料剩余条，旁边显示“按当前负载预计：1小时23分”。停机时写“已暂停”，不显示无穷大或虚构倒计时。
- 下部：净发电、实际输出、采能负载；储能数值放能量条悬停。
- 主按钮：“点火/停机”“采能负载”；自动续料开关放燃料侧栏，默认开启。
- 侧栏：能量、四组采能翼、燃料仓、结构预览/一键搭建、红石与安全。

燃料仓使用独立GUI和真实库存，不在主控做一套可取出的镜像物品槽。预计时间仅计算已投入预算；仓内待用燃料另列数量，防止把未知数据包燃料简单按同一种寿命相乘。

玩家提示示例：

> 封装一颗尚未点燃的微型恒星。放入恒星燃料仓，为微缩太阳供能。

> 太阳已进入余辉待机。储能腾出空间后会自动恢复。

## 8. 在MekGravity里如何落地

保持命名空间mekgravity和既有依赖，不改变现有引力堆的注册ID、数值和存档。

建议新增代码域 `dev.everyonemek.gravity.solar`：`SolarController`、`SolarStructure`、`SolarPart`、`SolarFuelRecipe`、`SolarMenu`、客户端`SolarRenderer`。以下只列职责，不是已注册类型。

关键边界：

1. 现有Structure把尺寸/坐标写成7，Ports也明确要求Controller。不能强行让太阳继承这些假设。先建独立9格校验器；仅将安全的long能量转发/预算等公共算法提取复用，回归旧堆。
2. 使用独立的 `stellar_fuel` 配方类型。现有FuelRecipe上限为1 PJ，低于本提案46.08 PJ，不能直接塞入现有配方或把long转成int。建议单配方上限10^17 J，所有乘加检查溢出，并限制单次预装仅够当前反应；能量余量与储电上限独立。
3. 主控持有唯一的能量、已付费燃料预算与首次点火标志；燃料物品归仓保存。接口转发同一份真实储能，不按翼片/接口复制库存或能量。
4. 结构失效、卸载即停工并关闭旧handler；重新成型恢复原预算。保护备用电不允许普通输出抽干；不补算离线发电。
5. 采能翼按组保存/校验等级，材料、能力朝向、自动弹出与GUI必须联动。角色映射来自结构实际位置，不以装饰纹理推断。
6. 正式灰模放 `art/models/mini-sun-v1`，按整机确认后再拆成方块模型、选择框、碰撞和渲染边界；不会在这份设计中把一张图冒充游戏模型。

## 9. 首版范围与验证

首版：单一9×9×9结构、一种长效燃料、四档约束/采能、独立仓、自动续料、点火/待机、可用long/FE物流和太阳动画。优先完成真实模型与资源预算，再加花样。

预留但不首发：向外扩建更多采能翼、可接其他燃料的配方、受控耀斑过载、特殊恒星产物。不开启默认爆炸或基地破坏，也不把日常补料变成随机事故小游戏。

实现验收必须检查：整份长寿命燃料的预算守恒；1小时模拟推进不按每单位FE循环；暂停/换档/拆装不能续满；四翼混级和单组升级上限；电满不浪费燃料；输入、主动/被动输出共享额度；老引力堆不受新接口影响。游戏内外观由用户验收。

## 10. 核对来源

- 本地实际发布件Mekanism/Mekanism Generators **1.21.1-10.7.19.85**：`GeneratorsChemicals`包含DEUTERIUM/TRITIUM/FUSION_FUEL。实际ID是 `mekanismgenerators:deuterium`、`mekanismgenerators:tritium`、`mekanismgenerators:fusion_fuel`，不是旧教程里的mekanism命名空间。
- 发布JAR配方 `data/mekanismgenerators/recipe/chemical_infusing/fusion_fuel.json`：1单位氘+1单位氚→2单位D-T；`rotary/fusion_fuel.json`提供液/气转换。制备选用化学品形态。
- 发布JAR `TileEntityPressurizedReactionChamber`：MAX_FLUID/MAX_GAS均10,000；现有 `data/mekanism/recipe/reaction/substrate/ethene_oxygen.json`证明原reaction类型支持物品、流体、化学品输入和仅物品产出。
- [ITER：Making fusion work](https://www.iter.org/fusion-energy/making-it-work)：磁约束与D-T等离子体作为设定灵感。实际太阳与实验聚变装置的燃料/形态不同；本设计不宣称球形微缩恒星是现实工程方案。
- [NASA：Sun Facts](https://science.nasa.gov/sun/facts/)：表面、日冕、日珥与磁场现象作为视觉参考，只用来确定动效方向，不据此推导游戏产电值。

所有功率、寿命、点火和配方消耗均为游戏设计提案，尚未做平衡或游戏内验证。
