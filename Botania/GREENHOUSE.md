# 魔力温室配方与扩展

游戏内用法见 [README](README.md#魔力温室)。本文件记录配方格式和开发边界。

## 原生花怎样转成配方

Botania 456 的产能花没有统一配方表。各花在自己的 BlockEntity 中判断物品、流体、世界条件和产量；不能只枚举物品注册表就推出任意花的需求。

温室采用两层结构：`GreenhouseNative` 将已核对的原生规则转换成一次加工计划，`GreenhouseWork` 执行材料、流体、工时、冷却和魔力结算。机器不运行隐藏花、不扫描附近掉落物，也不模拟羊、爆炸或其他世界事件。

| 公式 ID | 原生读取与转换 |
| --- | --- |
| `endoflame` | 从 Xplat 燃料接口读取具体 ItemStack 的燃烧值，读取原燃料上限、冷却和更新间隔。每次有效更新产 3 魔力、燃烧时间减半是固定快照中写在方法内的规则，由适配器明确换算。原花先减计时再产魔，温室舍弃最后不足一轮的脉冲，煤为 1,197 魔力。 |
| `gourmaryllis` | 调用原 `processFood`、食物营养值、连食倍率、魔力和时间函数。副本只用于纯计算；成功完成才把原 LAST_FOODS、STREAK_LENGTH、LAST_REPEATS 写回花物品。 |
| `spectrolus` | 读取原羊毛产量与按世界种子生成的颜色表。NEXT_COLOR、COLOR_SEQUENCE 随花保存；只有颜色匹配的一件羊毛会被消耗。羊不属于该物品配方。 |
| `thermalily` | 读取原流体标签、燃烧时间、每 tick 魔力和冷却；一格源流体换成 1,000 mB。原燃烧时间 ±1 tick 抖动归一为构造参数的周期，本固定构建为 600 tick／27,000 魔力，随后冷却 6,000 tick。 |
| `kekimurus` | 按原每口产量、工作间隔和原蛋糕七口换算；完整 CakeBlock 物品可供料。带方块状态的蛋糕不自动当完整蛋糕处理。 |
| `munchdew` | 使用原可食用方块标签、每片产量、工作间隔和冷却；连续吃叶，断料或容不下下一次产量后进入休息。 |
| `entropinnyum` | 从原热爆花读取满额收益，消耗一个真实 TNT 物品，用原 TNT 默认 80 tick 引信时间作为工时。不会生成爆炸实体，不接受无物品成本的复制 TNT。 |
| `rafflowsia` | 使用原魔法花标签、食花历史、收益函数和更新间隔；成功完成后保存原 LAST_FLOWERS、STREAK_LENGTH、LAST_REPEATS。 |

默认八种花及其浮空版本各由一个 JSON 公式配方声明。其他附属添加的燃料、带食物属性的物品、可食用树叶和标签中的流体可按相应规则被识别；这不代表自动支持所有附属产能花。依赖经验、生物、红石布局或周围环境的花需要另外的规则适配，不能无条件换成物品产魔。

JEI 的食物与食花配方显示首次使用的产量，并标出搭配条件；真实收益取决于装入花的历史。这两种变化收益使用纯展示槽，不交给 AE2 JEI Integration 作为固定样板输出，避免反复合成时交不齐魔力。其他固定收益和自定义固定配方使用常规魔力输出槽。

## 数据包固定配方

文件放在 `data/<命名空间>/recipe/<路径>.json`。例如下面是一个**自定义示例**，正式 JAR 不提供此纯白雏菊配方：

```json
{
  "type": "botanicalmekanism:mana_greenhouse",
  "flower": {"item": "botania:pure_daisy"},
  "ingredients": [
    {"item": "minecraft:milk_bucket"},
    {"item": "minecraft:wheat"}
  ],
  "fluid": {"id": "minecraft:water", "amount": 250},
  "mana": 1234,
  "ticks": 20,
  "cooldown": 30
}
```

- `flower`：保留在花槽内的 Ingredient，可用物品、标签或候选列表。每台温室放一朵。
- `ingredients`：每个 Ingredient 消耗一件，最多 16 项。需要两件同类材料就重复写两项，允许重叠标签，计数匹配不会重复使用同一件物品。
- `fluid`：可省略；需要时指定流体 ID、数量及可选组件，最大 16,000 mB。流体和物品允许混用。
- `mana`：固定配方需 1～1,000,000，必须能一次放入机内罐。
- `ticks`：加工时间，默认 1，范围 1～2,000,000。工作消耗基础 50 FE/t，支持能量升级，无速度升级。
- `cooldown`：完成后暂停供料的时间，默认 0，最大 2,000,000 tick。冷却不耗电，红石暂停也暂停倒计时。
- `formula`：默认 `fixed`。写上表的原生公式 ID 时，材料、产量、时间和条件由适配器计算；不要同时填写固定参数并期待其覆盖原规则。调整特定材料可另写固定配方，覆盖默认配方文件或删除不需要的公式配方。

固定配方至少需要一种实际消耗的物品或流体。物品的合成返还物进入返还槽；空间不足时不会开始扣料。配方按资源 ID 排序匹配，第一个可执行配方优先。数据包重载后，旧计划会重新核对配方对象和工作签名。

## 存储、物流与计算

- 一份材料完成时一次扣除并写入魔力，不按魔力点循环。满仓或断电时不吃掉未完成的材料。批次不复制成第二份虚拟库存。
- 输入 0～15，花槽 16，返还槽 17，能量槽 18，流体容器槽 19。花槽最大一件。容器输入与材料输入都归 Mek 物品输入页，花槽归辅料；输入／输出面同时包含两类输入和返还物，实际提取仍遵守槽位权限。
- 流体、Chemical 魔力和能源用 Mek 实际容器。装入花后，流体输入只接受该花配方适用的流体；存量不会因换花而清空。
- 冷却只保存在原 COOLDOWN 组件中，重新种花后也由原模组继续倒计时，不保留第二份旧值。咀叶花运行标记使用 CustomData 独立字段；食物、食花、颜色使用 Botania 原组件。拆温室还保存机内进度与签名。中途换花或改变已匹配材料会重新开始未完成加工，不额外生成魔力。
- 已匹配计划按物品完整组件／数量和流体快照复用；同 ID 配方被数据包替换也会失效。无匹配计划最多每秒重试一次，库存变化立即重试。没有每点魔力的迭代，也没有常驻附近实体扫描。
- 温室独有的 `GreenhouseSparkPort` 作为原火花的魔力池来源，仅暴露当前面允许提取的实际数量。其他加工机器仍使用原接收视图。Appbot 共存时只在可选兼容类上附加 SafeMana，不复制魔力库存。

## 开发入口

- `GreenhouseRecipe.java`：JSON／网络序列化；`GreenhouseNative.java`：版本适配和纯收益计算。
- `GreenhouseWork.java`、`ManaMachine.greenhouseTick`：匹配、缓存、进度及原子结算。
- `tools/greenhouse_resources.py`：默认公式配方；`client/GreenhouseJei.java`：配方展开与展示。
- `tools/botanical_models.py`、`client/GreenhouseFlowerRenderer.java`：原材质框架和实际装入花的原模型。
- `GreenhouseGameTests.java`：资源计量、原公式、固定数据包配方、供料、满仓／红石、状态保存、火花与侧面权限。
